# AlphaPing 产品需求文档

## 1. 产品定位

AlphaPing 是面向个人、团队和小型组织的自托管基础设施探针平台。它由 Cloudflare 原生控制面和安装在客户机器上的轻量 Rust Agent 构成，统一提供机器监控、服务可用性监控、容器监控、公开状态页和细粒度权限管理。

产品优先级按以下顺序排列：

1. 安全地知道机器和服务是否正常。
2. 用低成本保存足够定位问题的数据。
3. 提供现代、明快、可定制的公开探针体验，并让管理者快速扫描、比较和处理异常。
4. 允许将选定状态公开给游客，同时不泄露内部信息。
5. 保持 Agent 的低 CPU、低内存、可自动恢复和可静默升级。

## 2. 用户与角色

### 2.1 管理员

- 管理系统、组织、用户、角色、保留期和安全设置。
- 创建、修改、删除所有机器、服务、容器策略、探针任务和公告。
- 查看所有遥测和审计日志。
- 生成和撤销安装令牌、强制 Agent 检查更新。

### 2.2 普通用户

- 必须登录。
- 通过资源授权获得机器或服务的 `view` 或 `manage` 权限。
- `manage` 隐含 `view`，但不允许管理系统级设置、用户、密钥或其他未授权资源。
- 容器默认继承所属机器权限，可以被管理员显式收紧。

### 2.3 游客

- 不登录。
- 只能访问显式设置为公开的 dashboard、状态页和资源投影。
- 游客权限只能是查看，不存在管理权限。
- 默认不公开机器 IP、Agent 版本细节、请求头、请求体、容器环境变量、镜像仓库凭据和内部错误堆栈。

## 3. 多租户与工作区

- V1 必须从数据模型上支持多个 workspace，即使首个部署通常只有一个 workspace。
- 用户可以属于多个 workspace，并在每个 workspace 中拥有不同角色。
- 机器、服务、dashboard、状态页、公告、授权和保留策略都归属于 workspace。
- 所有业务查询必须显式带 `workspace_id`，禁止依赖客户端传入的资源 ID 推断租户。

## 4. 首次初始化

### 4.1 初始化条件

- 数据库中没有完成的 installation 记录时，普通路由必须重定向到 `/setup`。
- 初始化界面必须要求部署者输入由 Worker secret 提供的高熵 setup token，禁止“第一个访问者自动成为管理员”。
- setup token 验证成功后，在一个事务中创建 installation、默认 workspace、首个管理员和系统默认设置。
- 初始化成功后关闭公开注册，后续用户通过管理员邀请加入。

### 4.2 初始化步骤

1. 环境和 D1 migration 检查。
2. setup token 验证。
3. 创建管理员账号。
4. 创建 workspace 和默认 dashboard。
5. 设置数据保留期、默认采样周期和公开访问策略。
6. 显示下一步：添加机器或添加服务监控。

## 5. 机器监控

### 5.1 机器配置

- 管理员或有该机器 `manage` 权限的用户可以创建机器。
- 配置项至少包括名称、预期 IP 或主机名、标签、描述、采样周期、上报周期、离线阈值、是否启用容器监控。
- IP 是资产信息和检查目标，不是机器身份或认证凭据。
- 创建后生成 256-bit 一次性 enrollment token，默认 15 分钟过期，只允许成功使用一次。
- UI 必须提供 Linux/macOS Shell 和 Windows PowerShell 安装命令，并提供脚本查看、校验和与撤销入口。

### 5.2 机器列表

机器以紧凑 CSS Grid 展示，每个机器 item 必须包含：

- 名称、标签、操作系统和架构。
- 在线、降级、故障、离线或维护状态。
- CPU 使用率。
- 内存已用和总量。
- 主要存储卷已用和总量。
- 当前上传和下载速率。
- 自 Agent 注册以来或当前筛选周期内的累计网卡上行和下行流量。
- 最后上报时间和 Agent 版本。

状态定义：

- `online`：在离线阈值内收到报告，且没有达到故障阈值。
- `degraded`：仍在线，但一项或多项资源或探针达到警告阈值。
- `fault`：仍可通信，但达到严重阈值或关键探针失败。
- `offline`：超过离线阈值未收到报告。
- `maintenance`：处于人工维护窗口，不触发正常告警。
- `unknown`：从未成功上报或数据无法判断。

V1 默认机器资源阈值：CPU 达到 80% 为 `degraded`、95% 为 `fault`；内存或存储达到 85% 为 `degraded`、95% 为 `fault`。`maintenance` 优先于资源阈值。每次 durable report 只在状态实际变化时写入幂等事件；后续版本可以在不改变 Agent report 协议的前提下增加 workspace 或 machine 级覆盖值。

### 5.3 Dashboard 总览

总览必须展示：

- 机器总数。
- 在线机器数。
- 降级或故障机器数。
- 离线机器数。
- 当前总上传/下载速率。
- 当前筛选周期内的总上行/下行流量。
- 活跃服务故障数和正在进行的 incident 数。

总览数字必须可点击，点击后应用对应筛选，而不是只做静态展示。

### 5.4 机器详情

主 tab 默认为“概览”，首屏不自动展示大图表。必须包含：

- 当前 CPU、内存、存储、负载、运行时间、网络和系统信息。
- 可折叠的历史图表区域，展开后按时间范围加载。
- 与该机器有关的 Agent 探针任务结果图表。
- 最近事件、版本、配置同步状态和最后错误。

子 tab：

- `概览`
- `探针任务`
- `容器`，仅在容器监控开启时显示
- `事件`
- `配置`，仅对有 `manage` 权限的用户显示

## 6. 容器监控

- 容器监控是机器监控的下属能力，不形成独立顶层导航。
- Agent 自动探测 Docker Engine、Colima 提供的 Docker/containerd runtime，以及 Apple `container` runtime。
- 默认只读取运行时和容器状态，不读取容器环境变量、secret、挂载内容或日志正文。
- 每个容器展示名称、runtime、镜像、状态、健康状态、启动时间、重启次数、CPU、内存、网络和端口摘要。
- runtime 不可访问时必须显示权限或连接错误，不能将其误判为“没有容器”。
- 容器权限默认继承机器。管理员可以将单个容器设为对游客隐藏或对特定普通用户隐藏。

## 7. 探针任务

### 7.1 执行模式

支持两类执行器：

1. 目标机器自身的 Agent 检查指定 IP、域名、TCP 端口或 HTTP 资源。
2. 指定另一台已安装 Agent 的机器检查目标机器或资源。

Cloudflare 执行器在 V1 中支持 HTTP 和出站 TCP，不支持原生 ICMP Ping。需要 ICMP 的任务必须选择 Agent 执行器。

### 7.2 任务配置

- 任务类型：ICMP Ping、TCP Connect、HTTP/HTTPS。
- 自定义周期、超时、重试、连续失败确认次数和恢复确认次数。
- Agent 执行最短周期默认 5 秒，Cloudflare 中央执行最短周期默认 60 秒。
- 支持预期延迟阈值，并将结果映射为正常、降级、故障。
- 任务变更通过配置 revision 下发，Agent 必须回报已应用 revision。

## 8. 服务监控

V1 每个 workspace 最多配置 200 个未删除服务，以及这些未删除服务下合计 1,000 个检查。创建路径必须在最终写入语句中原子复核容量，达到上限时明确拒绝，不能创建随后被集合查询静默截断的资源。更高规模需要先增加服务端分页、调度容量和新的成本门禁。

### 8.1 服务与检查

一个服务可以包含一个或多个检查，并按策略汇总状态。检查类型：

- HTTP/HTTPS。
- TCP Connect。
- ICMP Ping，仅 Agent 执行。

HTTP 检查支持：

- Method、URL、超时、重定向策略和 TLS 验证开关。
- 自定义请求头，敏感值以 secret 引用保存，不回显明文。
- 可选请求 body，限制大小和支持 JSON、文本、表单。
- 预期状态码或状态码集合。
- 响应时间警告和故障阈值。
- 响应头存在、相等、包含、正则匹配断言。
- JSON body 使用 RFC 9535 JSONPath 选择值，并进行存在、类型、相等、范围、包含等断言。
- 文本 body 的包含和正则断言。
- 最大读取响应体大小，避免无界缓冲。

TCP 检查支持：

- 主机、端口、连接超时。
- 可选 TLS 握手和 SNI。
- 可选发送固定 payload 并检查响应前缀，必须有严格大小限制。

### 8.2 状态计算

- 每次检查结果为 `healthy`、`degraded`、`down` 或 `unknown`。
- 服务状态由关键检查优先级、失败确认窗口和维护窗口计算。
- 单次瞬时失败默认不直接形成故障，除非用户显式设置确认次数为 1。
- 状态转换必须生成不可变事件，并可关联 incident。

### 8.3 服务状态页

- 状态页以时间胶囊 item 展示每个时间桶的正常、降级、故障、维护或无数据状态。
- 胶囊必须支持 hover/focus tooltip，展示时间、成功率、延迟和失败摘要。
- 状态不能只依赖颜色，必须同时使用图标、文本、纹理或可访问标签。
- 页面展示当前状态、历史可用率、最近检查时间和进行中的 incident。
- 状态页支持公开或登录后访问，并支持资源级公开覆盖。

### 8.4 Incident 与公告

- 管理后台可以创建 incident，设置影响服务、严重级别、开始时间和当前状态。
- incident 支持按时间轴追加进展，更新内容不可静默覆盖，修改必须保留审计记录。
- 公告支持 `starts_at` 和 `expires_at`。超过 `expires_at` 后查询层立即不可见，清理 Worker 稍后物理删除。
- 支持 scheduled maintenance，并在状态胶囊中显示维护状态。

### 8.5 通知

- 管理员可以创建 Resend、SMTP HTTPS relay、Discord、Telegram、Slack 和 Bark 通知渠道；凭据必须加密保存且不可回显。
- 通知规则按 machine/service、异常维度和渠道绑定。机器维度至少覆盖 availability、resource threshold 和 recovery；服务覆盖 availability 和 recovery。
- 状态转换先形成不可变 telemetry event，再由独立通知 Worker 异步投递，不能阻塞 Agent durable ACK、检查结果事务或页面请求。
- 同一状态事件与同一渠道只创建一条内部投递记录，领取使用有界 lease。失败使用有界指数退避，最终失败可在管理页诊断和重试。外部渠道若没有幂等键支持，服务已接收但 ACK 丢失后可能重复发送；不得承诺外部 exactly-once。
- 维护窗口不发送普通异常通知；恢复通知可按规则启用。删除、停用渠道或规则必须立即阻止尚未认领的新投递。
- Cloudflare Worker 不直接连接任意 SMTP 端口；SMTP 通过部署者控制的 HTTPS relay 接入，Resend 使用官方 HTTPS API。

## 9. 动态导航与 Dashboard

- workspace 只配置机器监控时，不显示服务监控顶层入口。
- workspace 只配置服务监控时，不显示机器监控顶层入口。
- 两者都未配置时显示任务型空状态，引导创建第一个监控对象。
- 每个 dashboard 可独立配置公开或登录访问。
- dashboard 内的机器、服务、容器仍需经过资源级授权过滤，公开 dashboard 不等于其中所有资源自动公开。

### 9.1 公开探针外观

- 公开首页、机器列表、机器详情和服务详情采用现代、明快、面向个人访客的视觉，提供清晰状态、柔和表面和响应式布局。
- 管理员可以设置站点标题、介绍、配色、默认明暗模式与舒适/紧凑密度；保存前提供标明示意数据的实时预览。
- 导航栏使用 AlphaPing 的探测中心、回波圆弧与信号节点图标，不使用字母字标。管理员可用公开 HTTPS 图片地址或站内绝对路径替换 Logo；留空或加载失败时显示默认标志。外部图片由浏览器直接加载，不携带 Referer，不经过 Worker 代理抓取。
- 提供 Iris、Ocean、Mint、Sunset、Rose 五种明暗配色，默认明暗模式可跟随设备。
- 游客可以在自己的浏览器覆盖配色、明暗和密度，并恢复站点默认；个人偏好不写入服务器。
- 外观配置不改变资源公开策略。自定义域入口与公开路由采用同一主题配置，只允许经校验的文字、预设与 Logo 图片地址，不执行自定义 HTML/CSS/脚本或加载追踪资源。
- 主题配置复用既有公开查询和缓存，不增加轮询或历史预加载。

## 10. RBAC 与授权

权限能力：

- `view`：读取资源和允许范围内的历史数据。
- `manage`：修改资源配置、任务、阈值和公告，隐含 `view`。
- `admin`：workspace 全局权限，仅角色授予，不写入普通资源 grant。

资源类型：

- dashboard
- machine
- container
- service
- incident

授权规则：

1. workspace 管理员始终允许。
2. 显式 deny 优先于显式 allow，用于收紧继承权限。
3. 普通用户通过 membership 默认权限和 resource grant 合并获得权限。
4. 容器继承机器权限，存在容器覆盖时以覆盖为准。
5. 游客只根据 public policy 判断，不复用登录用户 grant。
6. API 和页面 loader 必须调用同一服务端授权函数，禁止只隐藏 UI。

## 11. Agent 生命周期

### 11.1 支持平台

V1 目标：

- Linux x86_64 和 aarch64，优先提供静态或最小依赖构建。
- macOS Apple silicon 和 Intel。
- Windows x86_64，aarch64 视 CI 和依赖支持情况进入 V1.x。

服务管理：

- Linux：systemd 和 OpenRC（supervise-daemon）；无 init 的环境明确拒绝自动服务安装。
- macOS：launchd daemon。
- Windows：Windows Service。

### 11.2 运行要求

- 空闲内存目标小于 30 MiB，稳定态 CPU 平均目标小于单核 0.5%。
- 默认 10 秒采样、60 秒 durable report，可由后台在允许范围内调整。
- 机器 dashboard 有可见 viewer 时，Agent 通过 live channel 每 10 秒发当前 snapshot；正常情况下界面数据年龄不高于一个采样周期加 2 秒网络/渲染余量。
- Live snapshot 是非持久加速层，不代替 durable report、本地 spool 或权威告警。Live 中断时 UI 标记降级并回退 D1 latest，不得误判机器离线。
- 本地缓冲固定使用 SQLite WAL，不使用仅存在内存的环形队列，也不实现自定义 append-only 文件格式。
- 每个 sample/check event 先持久化到 SQLite，只有收到服务端加密且通过认证的 durable acknowledgement 后才删除对应 delivery。
- DNS、连接、TLS、timeout、HTTP 408/429/5xx 等临时失败的重试次数不设上限，不因 attempt count 或离线时长删除 delivery。
- 退避使用 equal-jitter exponential backoff：从 1 秒开始，单次等待绝对上限 300 秒。服务长时间不可达时仍至少每 5 分钟尝试一次。
- 网络恢复事件可以触发 0-5 秒随机延迟后的立即尝试，任何成功都会重置退避。
- SQLite 默认上限 512 MiB，并保留至少 256 MiB 或磁盘 5% 的空闲空间。容量压力下先聚合未投递的低优先级原始样本，再在物理空间不足时按明确策略淘汰并上报数据缺口。
- 无限重试不等于无限磁盘。已经进入 delivery 且可能被服务端接收的 batch 不允许因重试次数被改写或删除。
- 进程崩溃由系统服务管理器自动重启，并使用退避防止重启风暴。

详细状态机、SQLite schema 和磁盘压力策略以 `11-telemetry-storage-and-retry.md` 为准。

### 11.3 自动更新

- 默认每 6 小时带随机抖动检查 GitHub Releases，并使用 ETag/条件请求。
- 下载前验证 TUF 风格元数据、目标文件长度、SHA-256 和离线签名。
- 更新使用临时文件、fsync、原子替换、健康检查和自动回滚。
- 管理面板可以下发“立即检查”和“强制更新到指定允许版本”命令。
- 强制更新仍必须通过签名和版本策略验证，服务器不能命令 Agent 执行任意 URL 或任意二进制。

## 12. 安全信道

- Agent 必须使用 TLS 1.3，并优先且默认只启用 `X25519MLKEM768` 混合密钥协商。
- 兼容性回退必须是显式部署选项，并在后台持续显示安全降级。
- enrollment token 高熵、短时、一次性，服务端只保存不可逆校验值。
- enrollment 完成后下发独立的数据加密密钥，服务端使用 master key 包裹后存入 D1。
- 上报 payload 先压缩，再使用 AES-256-GCM 加密。报文头作为 AAD，包含协议版本、Agent ID、key epoch、sequence 和时间。
- 服务端必须执行重放保护、时间偏差检查、payload 大小限制和速率限制。
- 密钥按周期和事件轮换，撤销机器后旧密钥立即失效。
- 详细协议以 `05-agent-protocol-security.md` 为准。

## 13. 数据保留与删除

- 系统设置允许配置原始遥测、5 分钟汇总、事件、审计日志和已过期公告的保留期。
- 删除 workspace、机器或服务时先进入可恢复删除窗口，再由 retention Worker 物理清理。
- retention Worker 必须幂等、分批、可续跑，并记录游标、删除量和错误。
- 原始遥测、汇总和状态事件必须写入 D1，并通过 resource/time/resolution 查询 API 访问。
- 每个 60 秒 report 使用 `telemetry_blocks_5m` 的一个固定分钟 slot 保存全部 10 秒 samples；raw 查询从 block slots 还原每个 sample。
- R2 只保存显式导出或备份 artifact，不参与 dashboard 和历史图表的在线查询。
- 备份与恢复必须覆盖 D1 配置、权限、密钥包裹记录和 telemetry tables。

## 14. 非功能需求

### 14.1 性能

- 机器列表在 500 台机器下首屏服务端响应目标小于 500 ms，不含公网网络延迟。
- Dashboard 不加载折叠图表的数据。
- 历史查询必须按时间范围和资源分页，不允许无界扫描。
- 所有长列表使用虚拟化、分页或增量加载。

### 14.2 可用性

- Agent 上报和检查结果处理必须至少一次，消费者必须幂等。
- Dashboard 最新状态允许最终一致，目标延迟不超过一个上报周期加 15 秒。
- 公开状态页在控制面短时故障时应利用不超过 5 分钟的缓存展示最近有效快照，并标记更新时间；公开 dashboard 或资源策略撤销后的旧投影最多允许在该窗口内继续可见。

### 14.3 可访问性

- 目标 WCAG 2.2 AA。
- 所有状态有非颜色表达。
- 所有图表有文本摘要或表格替代。
- 键盘可完成导航、筛选、对话框和表单操作。

### 14.4 可观测性

- Worker 使用结构化日志和 request/correlation ID。
- 不记录 token、密钥、完整请求头、完整 payload 或用户 secret。
- 记录 D1 持久延迟/写入量、Live Hub 连接/消息/hibernate 成本、Agent spool backlog、版本分布和更新失败率。

## 15. V1 验收标准

1. 新部署者可以通过安全 setup 流程创建首个管理员。
2. 管理员创建机器后，可以复制脚本安装 Agent，5 分钟内在 dashboard 看到最新状态。
3. 机器离线、恢复和阈值越界能形成正确状态和事件。
4. Docker/Colima/Apple container 至少在各自支持环境中完成探测和状态展示。
5. 可以创建 HTTP、TCP 和 Agent ICMP 检查，并配置响应断言和周期。
6. 公开状态页可以展示状态胶囊、incident 时间轴和自动过期公告。
7. 管理员、普通用户和游客的资源权限通过服务端集成测试。
8. 上报包在抓包时不可读取业务 payload，重放、过期 token 和撤销密钥会被拒绝。
9. retention Worker 能按设置清理 D1 测试数据和过期 export/backup artifacts，重复执行不产生错误结果。
10. Agent 可以完成签名更新、失败回滚和面板强制检查。

## 16. V1 非目标

- 不提供任意命令执行、远程 Shell 或文件浏览。
- 不采集容器 secret、环境变量全文或日志全文。
- 不承诺 Cloudflare Worker 的 ICMP Ping 或固定探测地理位置。
- 不在 V1 提供 Kubernetes 集群级监控。
- 不在 V1 提供完整告警通知渠道市场，先保留事件/通知接口。
- 不将 Analytics Engine 作为租户遥测的权威存储，因为其固定三个月保留期无法满足自定义删除。

## 2026-09 主题与公开体验

公开探针页面以现代消费级产品风格呈现，支持管理员持久化品牌标题、介绍、主题配色、默认明暗与密度，以及游客浏览器内的个性化覆盖。风格重构不扩大公开数据范围；缺失和陈旧数据必须明确表达。
